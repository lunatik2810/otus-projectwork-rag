# Чанкинг. 
Текст разбивается на куски по границам предложений (после точки с заглавной буквой) и по переводам строк. Затем куски склеиваются в чанки с ограничением 480 токенов на чанк и перекрытием 20 токенов между соседними — чтобы смысл, разорванный границей, не терялся. Количество токенов каждого куска считается заранее, одним проходом токенизатора, чтобы не считать дважды.

Разбиваем либо после знака конца предложения перед заглавной буквой, либо по переводу строки. Используем lookbehind (?<=\r?\n), чтобы перевод строки НЕ удалялся и оставался в первой (предыдущей) части.

```code c#
 var pattern = @"(?<=[.!?…]\s*)(?=[А-ЯЁA-Z])|(?<=\r?\n)";

 var parts = Regex.Split(text, pattern)
     .Where(p => !string.IsNullOrWhiteSpace(p))
     .ToArray();
```

# Сущности
Четыре сущности:
 - Documents — метаданные о файле: путь (уникальный), имя, MD5-хеш, даты создания и обновления.
 - Chunks — куски текста: ссылка на документ, номер по порядку внутри документа, сам текст, число токенов. Уникальность пары «документ + номер» защищена индексом.
 - Embeddings — векторы: связь один-к-одному с чанком, сам вектор как BLOB, размерность.
 - ChunksFts — виртуальная полнотекстовая таблица (FTS5) для быстрого поиска по словам (BM25).
 - Ключевой трюк — синхронизация текста и полнотекстового индекса через триггеры:
	* при вставке чанка триггер автоматически кладёт его текст в FTS-таблицу, причём с тем же внутренним номером (rowid), что и у самого чанка — так записи всегда совпадают;
	* при удалении вектора чанка второй триггер автоматически удаляет соответствующую строку из FTS. Это позволяет «вычистить» полнотекстовый индекс одной операцией при переиндексации документа.
Соединения к базе открываются через фабрику, которая включает внешние ключи и режим WAL (журнал, позволяющий читать базу во время записи). Репозитории работают с уже открытым соединением и переданной транзакцией — владеет транзакцией вызывающий код, это даёт атомарность «всё или ничего» на каждый файл.

Получается вектор из 384 чисел.

# Таблицы SQLite
Сама БД должна называться vectorDb

Хранит информацию об исходном файле.
```SQL
CREATE TABLE Documents
(
    Id INTEGER PRIMARY KEY AUTOINCREMENT,

    SourcePath TEXT NOT NULL UNIQUE,

    FileName TEXT NOT NULL,

    ContentHash TEXT NOT NULL,

    CreatedAt TEXT NOT NULL,

    UpdatedAt TEXT NOT NULL
);
```

Хранит разбитый на чанки текст.
```SQL
CREATE TABLE Chunks
(
    Id INTEGER PRIMARY KEY AUTOINCREMENT,

    DocumentId INTEGER NOT NULL,

    ChunkIndex INTEGER NOT NULL,

    Text TEXT NOT NULL,

    TokenCount INTEGER NOT NULL,

    FOREIGN KEY (DocumentId)
        REFERENCES Documents(Id)
);
```

Хранит embedding каждого чанка. Для multilingual-e5-small размерность — 384.
```SQL
CREATE TABLE Embeddings
(
    ChunkId INTEGER PRIMARY KEY,

    Vector BLOB NOT NULL,

    Dimensions INTEGER NOT NULL,

    FOREIGN KEY (ChunkId)
        REFERENCES Chunks(Id)
);
```

FTS5-индекс для полнотекстового поиска BM25.
```SQL
CREATE VIRTUAL TABLE ChunksFts
USING fts5
( 
    Text,

    content='Chunks',

    content_rowid='Id'
);
```

# multilingual-e5-small
Для получения Embeddings нужно использовать модель model_O4.onnx и файлы к ней tokenizer.json, tokenizer_config.json. У этой модели есть особенности:
 - Обязательные префиксы "query: " / "passage: ". Модель обучена на парах «запрос-документ» с разными префиксами. Смешивать их нельзя:
 -- индексируемые документы — с префиксом "passage: " → E5SmallEmbedder.EmbedAsync();
 -- пользовательский запрос — строго с "query: " → E5SmallEmbedder.EmbedQueryAsync().
 - Нижний регистр перед эмбеддингом. intfloat/multilingual-e5-small обучена на нижнем регистре (в отличие от многих других моделей). Рекомендация с карточки модели: «lowercase the text and prepend query:/passage:». 
 - L2-нормализация при записи (уже реализовано ✅ → дешёвый косинус). 
 - поищи сам особенности, может быть найдешь что-то еще при реализации, предложи сделать.

# LangGraph‑граф (Corrective RAG)

Поиск — гибридный: BM25 находит документы по точному совпадению ключевых слов, векторный поиск — по смыслу запроса. Результаты объединяются через Reciprocal Rank Fusion (RRF): итоговый ранг документа зависит от его позиций в обоих списках. Это позволяет одинаково хорошо отвечать на семантические вопросы («как работает авторизация») и точечные («где используется `TOKEN_EXPIRY_HOURS`»).

```
User Query → Rewrite Query → Retrieve (hybrid: BM25 + vector → RRF)
  → Grade Chunks (relevant? yes/no)
    → enough relevant → Generate Answer → Return answer + sources
    → too few relevant → Broaden Query → Retrieve (max 2 loops)
```
